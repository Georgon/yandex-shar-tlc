# Идеи продуктовых улучшений и A/B-тестов — версия 23.08

Четыре целевые гипотезы. Для каждой: проблема, метрики с назначением и
базлайнами из витрин, дизайн эксперимента, правила формирования выборки и
критерии вывода.

**Граница данных.** Базовые уровни и проблемные сегменты считаются по TLC
(базлайны в таблицах). Но в TLC нет показов предложений, кликов, отмен,
онлайн-времени водителей и действий пользователей до заказа — для проверки
самих гипотез нужен сбор новых событий внутри приложения.

## H1. Округление стоимости поездки в пользу чаевых

**Гипотеза.** Если пассажиру, который не выбрал чаевые или выбрал меньше $5,
предложить округлить итоговую стоимость до ближайших $0,50 («Округлить до
$15,50? Дополнительные $0,27 получит водитель»), средние чаевые на завершённую
поездку увеличатся — без снижения крупных чаевых (при $5+ не показывается) и
без раздражения (максимум надбавки $0,49).

**Проблема.** 80,9 % поездок — без чаевых; «добавить пару долларов» — барьер,
надбавка до полтинника — мелочь.

**Метрики, которые уже можно получить (с базлайнами):**

| Метрика | Для чего | База |
|---|---|---|
| Средние чаевые на все поездки | основная: sum(tips)/поездки | ~$1,20 |
| Доля поездок с чаевыми | как часто дают | 19,1 % |
| Медиана чаевых среди дающих | поведение платящих (устойчивее среднего: хвост $10+ тянет среднее к $6,30) | $4,73 |
| Доля чаевых <$5 | размер целевой аудитории | 52,3 % дающих |
| Доля чаевых $5+ | контроль крупных | 47,7 % дающих |
| Стоимость поездки | расчёт округления | чек ~$33 |

Параметры механики по сырым данным: окно надбавки **$0,10–0,49** → показ
**61,5 % поездок** (у 36,7 % хвостик <10¢ — пропуск; 1,8 % уже круглые);
средняя надбавка **$0,285**; потолок +13 % к чаевым, цель при конверсии
15–30 % — **+2–4 %**.

**Новые метрики в приложении:** показы предложения; доля согласившихся;
средняя сумма округления; допчаевые на показ; переход 0 → положительные;
количество отказов (ограничение частоты); закрытие экрана оплаты
(раздражение).

**Эксперимент.** A/B по `passenger_id` (один человек — один вариант), 2–4
полные недели (декабрь исключить: всплеск чаевых +22–33 %). Сравнивать все
поездки групп, не только согласившихся.

**Выборка.** Включить: завершённые поездки, оплату картой/приложением, без
возвратов, пассажиров с разной историей чаевых. Исключить: наличные, тестовые
и дублирующиеся заказы, технические ошибки оплаты. Сбалансировать: дни недели,
время суток, стоимость, районы, новые/постоянные, история чаевых.

**Принимается, если:** средние чаевые по всем выросли; доля поездок с чаевыми
увеличилась; чаевые $5+ не уменьшились. Соглашаются часто, но прирост мал →
менять минимальную сумму; раздражение (закрытия экрана оплаты) → ограничить
частоту. Риск: наличные чаевые невидимы — эффект по карточным.

## H2. Бонус за выполненные поездки в дефицитных районах и часах

**Гипотеза.** Если заранее информировать водителей о подтверждённом спросе и
предлагать бонус за выполненные поездки в дефицитных районах и часах
(«Выполните поездку из этого района с 04:30 до 05:30 — получите дополнительно
X % к оплате поездки»), больше водителей будет принимать такие заказы и
ожидание сократится; платформа не платит при отсутствии поездок: нет
выполненной поездки — нет выплаты. Процент X не задаётся заранее: для каждого
района и часа система рассчитывает минимальный процент, который обеспечивает
нужный отклик водителей и сохраняет положительную экономику программы.

**Проблема.** Водители не выходят в дефицитные окна из-за неопределённости
заказов → долгая подача, отмены, потерянные поездки. 04:00 — худший час (P90
10,8 мин; >15 мин — 3,5 %), при этом занятый час в 04:00 — **$76,4, максимум
суток** (днём $59–62): премия есть, но риск лотереи на водителе.

**Механика — выплата только при выручке:**

- Платформа видит подтверждённый спрос (например, предзаказы в аэропорт на
  05:00) и предлагает ближайшим водителям бонус за выполненную поездку из
  района в окне 30–60 мин. **Водитель не обязан стоять в районе** — бонус
  привязан к выполненному заказу, не к присутствию.
- Поездка состоялась → есть выручка → часть её ушла в бонус; поездки нет →
  ни выручки, ни выплаты. Риск нулевого спроса на платформе не лежит.
- Выплата рассчитывается по формуле:
  `бонус = driver_pay × bonus_rate(район, час)`. Оптимальный `bonus_rate` —
  минимальный проверенный процент, при котором отклик водителей достигает
  целевого уровня, а ожидаемая маржа дополнительных поездок остаётся выше
  ожидаемой суммы бонусов.
- Отмена после назначения водителя компенсируется из комиссии за отмену или
  платы за бронирование — не из бюджета программы.

**Метрики TLC (базлайны):** P50/P90 подачи (4,1/9,3 мин; 04:00 — 10,8); доля
>15 мин (2,0 %; 04:00 — 3,5 %); поездки по району-часу (Рокавеи/СИ P90 13–15);
доход за занятое время ($59–76/час — ориентир для допустимого процента
бонуса; низ — ставки TLC с 01.03.2026 $0,681/мин + $1,283/миля); предзаказы (1,19 %,
04:00 ×4,3); поездки соседних районов (переток).

**Новые метрики платформы:** предложенные бонусные окна; отклик на офферы
(главный индикатор достаточности процента); применённый процент бонуса;
зависимость отклика водителей от процента; доля откликнувшихся, выполнивших
поездку; онлайн-время; сумма выплаченных бонусов (возникает только при
выручке); доля окон без поездок (расходов нет, но прогноз ошибся); стоимость
доппоездки.
Экономика: `эффект = маржа доппоездок − бонусы − расходы`; отрицательный →
окно не открывать.

**Эксперимент.** По пассажирам нельзя (водители влияют на весь район) →
единица: **район × интервал**, switchback (пн 04:00–05:00 вкл / след. пн
выкл). Старт: офферы 2–3 ближайшим водителям, окна 30–60 мин, дефицитные
районы, в первую очередь под подтверждённые предзаказы (связка с H4 —
забронированные аэропортовые поездки и есть подтверждённый спрос). 6–8 недель.

**Выборка.** 6–8 районов с устойчивым долгим ожиданием, достаточным объёмом,
похожей динамикой, без единичных аномалий. Сравнивать одинаковые дни/часы/
сезон/погоду/движение (штормовые дни уровня 25.01 и 23.02 — исключать по
заранее объявленному правилу). Учитывать соседние районы. **Окна без поездок
не исключать** — расходов они не создают, но это главный сигнал ошибки
прогноза.

**Принимается, если:** P90 и доля >15 мин снизились; поездок стало больше;
соседние районы не пострадали; маржа доппоездок покрыла бонусы. Экономика на
грани → уменьшать процент или число окон; водители не откликаются →
пересчитать процент по фактической кривой отклика; откликаются, но ожидание не
меняется → неверные районы или время. Гейминг: бонус только за реальные
поездки с пассажиром, следить за аномально короткими поездками в бонусных
окнах.

## H3. Более удобная точка посадки за скидку

**Гипотеза.** Если предложить пройти 10–200 м до точки, куда водителю легче
подъехать, и дать скидку, время подачи и отмены уменьшатся: геолокация
пассажира — не всегда удобная точка посадки (односторонние улицы, запреты
остановки, толпа после мероприятий, дворы).

**Проблема.** Вечер 22:00–00:00: P90 9,7–10,0 мин и >15 мин 2,5–2,7 % **при
свободных дорогах** (16,9–17,5 миль/ч) — дело в «последних сотнях метров», не
в пробках.

**Метрики TLC (базлайны):** время запрос→подача (P50 4,1/P90 9,3); P50/P90 по
зонам-часам (вечер 9,7–10,0); район и час; скорость движения (отделяет сложную
точку от пробки; вечер 16,9–17,5 миль/ч).

**Новые метрики приложения:** показы альтернативной точки; доля принятых;
предложенная дистанция; фактическое время подхода; время подачи к новой точке;
**расстояние подачи водителя** (в TLC отсутствует — только время); размер
скидки; отмены после принятия.
Объединённая метрика: **доля пассажиров, забранных за ≤10–15 мин** (учитывает
и отмены; платформенная).

**Эксперимент.** A/B по запросам: A — обычная точка, B — предложение со
скидкой. Сравнивать всю тестовую группу, включая отказавшихся (intent-to-treat
— «только согласившиеся» смещены в сторону мобильных). 3–4 недели. Скидка от
экономии: минута подачи ≈ $0,5–0,7 машино-времени.

**Выборка.** Только точки с безопасным пешим маршрутом, реальным сокращением
подачи, разрешённой остановкой, расстоянием 10–200 м. В приоритете ситуации,
где перенос точки позволяет водителю избежать длинного разворота, объезда,
одностороннего участка или локального затора. Исключить: ограниченную
мобильность и WAV-заказы, небезопасные маршруты, непогоду, запрещённые
переходы, ошибки геолокации. Сбалансировать: районы, время, дистанция, размер
скидки.

**Принимается, если:** P90 подачи снизился; доля забранных за 10–15 мин
выросла; отмены не выросли; экономия покрыла скидки. Подача быстрее, но
соглашаются редко → менять скидку,
дистанцию, формулировку. Риск: не предлагать 00:00–05:00 и вне освещённых
точек; опция добровольна; зонный эффект консолидации мерить switchback-ом.

## H4. Бронирование поездки в аэропорт после просмотра маршрута

**Гипотеза.** Если пользователю, который заранее рассчитывает стоимость
поездки в аэропорт, сразу предложить забронировать машину на дату и время
(водитель не закрепляется заранее — заказ уходит подходящему за 10–30 минут до
подачи), конверсия из просмотра в поездку вырастет: сейчас проверивший цену
может забыть, уйти к конкуренту или не найти машину, а платформа теряет
информацию о будущем спросе.

**Проблема.** Аэропорты — 8,4 % поездок и **20,6 % выручки** (чеки JFK $85 /
LGA $69 / EWR $112 против $33); в аэропорт — ~33 тыс. поездок/день. Предзаказы
вчетверо чаще аэропортовые, но их лишь 1,19 % — вход в воронку почти не
используется, при том что функция планирования уже в проде. Каждое
бронирование — подтверждённый будущий спрос (топливо для бонусных окон H2).

**Метрики TLC (базлайны):** аэропортовые поездки (~33 тыс./день в аэропорт);
время поездки по району-часу (рекомендация выезда); стоимость (чеки выше);
время подачи (P90 JFK/LGA 13–14 мин); доля предзаказов (1,19 %).

**Новые метрики приложения:** просмотры расчёта; показы кнопки бронирования;
**конверсия просмотра в бронирование — главная**; время бронирование→поездка;
изменение времени брони; отмены брони; фактическая подача против плановой;
отклонение цены от предварительной; прибыль с брони.
Воронка: просмотр → показ → «Забронировать» → бронь → назначение →
своевременная подача → завершённая поездка.

**Эксперимент.** Пользователи, выбравшие аэропорт и будущую дату: A — только
расчёт; B — расчёт + рекомендуемое время выезда + кнопка бронирования.
Распределение по `passenger_id`. 4–6 недель. Результат — по всем, кому
показали расчёт, не только по оформившим.

**Выборка.** Включить: аэропорт назначением, будущая дата, горизонт ~24–48 ч,
корректный расчёт. **Повторные расчёты одного пользователя — в одну сессию**
(иначе один человек посчитается пятью). Сбалансировать: аэропорты, районы,
время вылета, день недели, горизонт, стоимость, новые/постоянные.

**Принимается, если:** конверсия просмотр→бронь выросла; аэропортовых поездок
стало больше; машины вовремя; отмены/жалобы не выросли; цена не расходится с
обещанной; брони прибыльны. Бронирований больше, но опоздания → проблема в
механике назначения; бронируют, но отменяют → проверять цену, условия отмены,
точность времени. Риски: форс-мажор для штормов (25.01 −61 %, 23.02 −74 %);
P90 спонтанных заказов тех же зон — guardrail; «из аэропорта» по номеру рейса
(там предзаказов 0,24–0,34 %) — следующая волна.

## Общие требования к качественному эксперименту

1. **Одна основная метрика** — до запуска, не подбирать после.
2. **Минимальный полезный эффект** — что оправдывает внедрение.
3. **Размер выборки** — из текущего значения и разброса метрики.
4. **Продолжительность** — несколько полных недель (недельная сезонность).
5. **Контрольная группа** — иначе эффект не отделить от сезонности.
6. **Защитные метрики** — безопасность, прибыль, опыт не должны ухудшаться.
7. **Правила исключения данных — до старта** (включая погодный критерий для
   штормовых дней уровня 25.01/23.02).
8. **Проверка распределения** — группы похожи по районам, времени, стоимости,
   типам пользователей.

**Кандидаты следующей волны:** позиционные стимулы периферии (поглощены
бонусными окнами H2; Рокавеи и Стейтен-Айленд — первые кандидаты в районы); апселл
«Сделать $5» после округления H1; бронирование из аэропорта по номеру рейса;
шеринг-гарантия скидки; заметность WAV.

*Базлайны: витрины `nyc.mart_*` и запросы к `nyc.trips` (silver, 326,8 млн
строк). Все доли — отношения сумм; ожидание — только по поездкам с валидным
ожиданием.*
